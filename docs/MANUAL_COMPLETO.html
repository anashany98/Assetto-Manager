AC-MANAGER | Manual Completo Produccion

Manual tecnico-operativo integral para dejar la plataforma lista para produccion, robusta contra fallos y preparada para despliegues comerciales repetibles.

Topologia objetivo: 4 estaciones + 1 PC Master LAN cableada Kiosko por tablets Licencias por modulos

Fuente: codigo real del repositorio (backend/, frontend/, agent/, tools/license-manager/) y runbooks de docs/.

1) Resumen Ejecutivo

Superficie backend
249
Rutas HTTP/WS detectadas en routers.
Modelo de datos
28
Entidades SQLAlchemy en models.py.
Escenario base
4 + 1
4 simuladores + 1 operador.

Objetivo de produccion

  • Operacion fluida en sesiones, kiosko y streaming.
  • Resistencia ante caidas de agentes, red o procesos.
  • Despliegue repetible para multiples clientes.
  • Control de licencias por modulos y seguridad por scopes.

Estado real actual

  • Stack completo en produccion: backend + frontend + agente + portal de licencias.
  • Observabilidad integrada: /health, /health/live, /health/ready, /system/metrics, /system/alerts.
  • Hardening implementado en arranque de backend para variables criticas.
  • Punto clave de arquitectura: WS usa estado en memoria, por defecto se trabaja con UVICORN_WORKERS=1.

3) Arquitectura de Referencia

Topologia recomendada

  • PC Master: backend + frontend build + DB + backups.
  • SIM 1..4: agente + Assetto Corsa + OBS.
  • Tablets kiosko: acceso web /kiosk + codigo de estacion.
  • TV y publico: vistas /tv/*, spectator y ranking.

Canales en tiempo real

  • WS agente: /ws/telemetry/agent.
  • WS cliente: /ws/telemetry/client.
  • Multi-worker solo si se activa Redis pubsub (WS_PUBSUB=redis + REDIS_URL).

Decisiones tecnicas que afectan estabilidad

  • Single worker por defecto evita inconsistencias WS/in-memory.
  • Scheduler corrige estados stale y lobbies huerfanos.
  • Frontend servido por backend en prod reduce complejidad de despliegue.

4) Flujo de Funcion End-to-End

4.1 Arranque del sistema

  1. Backend inicia y valida config de runtime estricta en produccion.
  2. Scheduler activa jobs de mantenimiento y sincronizacion.
  3. Agentes se registran por POST /stations/ y abren WS con identify.
  4. Dashboard detecta estaciones online y estado de servicios.

4.2 Flujo de estacion

  1. Agent envia heartbeat/hardware y telemetria.
  2. Backend puede enviar comandos de launch/stop/scan/mod sync.
  3. Si la estacion cae, sweep de stale la pasa a offline automaticamente.

4.3 Sesiones de juego

  1. Inicio: /sessions/start o /control/station/{id}/launch.
  2. Lobby multiplayer: create/join/ready/start en /lobby.
  3. Fin: /sessions/{id}/stop y persistencia de resultados.

4.4 Kiosko y reservas

  1. Tablet entra en /kiosk y se empareja por codigo de estacion.
  2. Reserva en /bookings con control de solapamientos.
  3. Si hay pagos habilitados, checkout en /payments/checkout.

4.5 Telemetria y TV

  1. Agente emite eventos por WS y backend los reenvia a clientes.
  2. Laps pueden guardarse desde eventos live y/o upload de session completa.
  3. TV spectator usa stream_url de estacion o fallback por STREAM_BASE_URL.

4.6 Update de agentes

  1. Admin sube ZIP por POST /system/update.
  2. Backend guarda manifiesto de version + hash + firma opcional.
  3. Agente consulta /system/version, descarga y actualiza.

7) Seguridad y Licencias

Capas de seguridad

  • JWT admin para panel privado y operaciones administrativas.
  • Client token por header X-Client-Token para kiosko/public.
  • Agent token por header X-Agent-Token para estaciones.
  • Scopes finos para clientes y agentes (CLIENT_TOKENS*, AGENT_TOKENS*).

Hardening activo en backend

  • Validacion de secretos obligatorios en produccion.
  • Bloqueo de placeholders en claves sensibles.
  • Bloqueo de CORS wildcard en produccion.
  • Query-token desactivado por defecto en produccion.
  • Headers de seguridad + rate limiting.

Licencia por modulos

  1. Portal emite JWT RS256 con issuer VRacing Sim Center.
  2. AC-MANAGER valida con clave publica configurada.
  3. Backend habilita modulos segun modules de la licencia.

Importante: la revocacion actual es administrativa (portal). Para revocacion efectiva inmediata se recomienda validacion online o TTL corto.

8) Streaming LAN y Latencia

Que es razonable esperar

  • Muy fluido: 120-250 ms e2e en perfil WebRTC LAN.
  • Aceptable: 250-450 ms.
  • Problema: mayor de 450 ms o stutter.

Referencia perceptual

  • Interaccion UI: ideal debajo de 50 ms.
  • Streaming spectator: debajo de 200 ms se siente fluido para publico.
  • Latencia de monitor directo (<20 ms) no es realista en pipeline encode/red/decode.

Perfil recomendado para 4 estaciones cableadas

backend/.env
STREAM_BASE_URL=http://<MEDIA_SERVER_IP>:8889/live
STREAM_FALLBACK_MODE=webrtc

agent/config.json (cada estacion)
"stream_url": "http://<MEDIA_SERVER_IP>:8889/live/station1"

OBS encoder (cada estacion)
- 1280x720 @ 60fps
- CBR 4500-6000 kbps
- keyframe 1s
- preset low latency

9) Despliegue Produccion

9.1 Master PC (recomendado 1 comando)

powershell -ExecutionPolicy Bypass -File .\scripts\setup_master_pc.ps1 `
  -ServerIp "192.168.1.50" `
  -DatabasePassword "PASSWORD_FUERTE" `
  -AdminUsername "admin" `
  -AdminPassword "PASSWORD_ADMIN"

9.2 Flujo manual

  1. scripts/deploy_prod.ps1 -DatabaseUrl "postgresql://..."
  2. Verificar /health, /health/live, /health/ready.
  3. Abrir dashboard en http://server-ip:8000.
  4. Crear primer admin con /auth/users/setup.

  -ServerIp "192.168.1.50" `

  -ServerUrl "http://192.168.1.50:8000" `
  -Username "admin" `
  -Password "<PASS>"

11) Backup y Recuperacion

Backup diario programado

powershell -ExecutionPolicy Bypass -File .\scripts\schedule_backup.ps1 `
  -EnvFile "backend\.env" `
  -BackupDir "D:\AC-BACKUPS" `
  -RetentionDays 30 `
  -StartTime "03:00"

Backup manual

powershell -ExecutionPolicy Bypass -File .\scripts\backup_db.ps1 `
  -EnvFile "backend\.env" `
  -BackupDir "backups" `
  -RetentionDays 7

Restore PostgreSQL

pg_restore --clean --if-exists --no-owner --no-privileges `
  -d "postgresql://user:pass@host:5432/ac_manager" `
  "C:\ruta\ac_manager_YYYYMMDD_HHMMSS.dump"

Politica recomendada

  • Regla 3-2-1 y prueba de restore mensual.
  • Backup obligatorio antes de release/migracion.

Objetivo comercial

13) Mejoras recomendadas (competencia vs tu app)

P0 - impacto inmediato

  • Servicio Windows obligatorio para backend en todos los clientes.
  • Smoke tests post-deploy automatizados (login, station online, launch, stop).
  • Simulacro de restore mensual documentado.

P1 - valor diferencial

  • Canary rollout de updates de agente (1 estacion antes de lote).
  • Control plane central multi-sede para soporte remoto.
  • Revocacion de licencias efectiva (online check opcional o TTL corto).
  • Paneles por rol (operador, tecnico, gerente).

P2 - escalado SaaS

  • Observabilidad centralizada (Prometheus/Grafana/ELK).
  • Facturacion y renovacion de licencias automatica por tenant.
  • Matriz de producto (Lite/Pro/Enterprise) sobre feature flags.

14) Posibles problemas en el futuro

RiesgoImpactoMitigacion
Multi-worker sin Redis WS Inconsistencia de comandos y estados Forzar UVICORN_WORKERS=1 o habilitar Redis pubsub completo.
Dependencia de un solo master PC Parada total del local Imagen de recuperacion + backup + equipo de reemplazo.
Revocacion de licencia offline limitada Control comercial parcial Validacion online opcional + vencimientos mas cortos.
Crecimiento de carga sin tuning DB Latencia alta y timeouts Indices, ajustes de pool y pruebas de carga periodicas.
Streaming inestable por red no aislada Mala experiencia TV Switch/VLAN dedicados, bitrate adecuado y cableado total.
